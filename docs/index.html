Design of Agentic samples featuring LangGraph and DeepAgents

This document specifies a shared execution path for console, scripted, and Angular clients using LangGraphAgent. It defines component responsibilities, interrupt handling, and the samples.

1. Execution architecture

Console, scripted, and Angular clients use the same execution path. The diagram shows where client interaction, workflow policy, and agent behavior belong.

Sample selection and startup

All samples use one launcher: python -m agent_runtime. SampleCatalog reads samples/*/sample.json to discover each sample and its workflow, options, and scripted inputs. Console and browser menus use the same catalog.

The launcher selects the application for the chosen client:

ClientApplication responsibilityScripted prompts
Console or static inputConsoleApplication prepares and runs the selected sample. Static input runs once; interactive input allows sample switching.Python ScriptPrompter supplies requests through ConsoleClient.
Angular browserAngularApplication starts the web listener. HTTP handlers create sessions; WebConversation manages their runs and resources.TypeScript WebScriptPrompter supplies browser prompts and advances after each completed turn. Requests reach WebConversation over HTTP.

Starting a new conversation creates fresh models, resources, and conversation state. Workflows and agents use build_model to obtain real or scripted models. Model choice is independent of prompt source: scripted prompts can drive real models.

Prompt sequencing belongs to the client. Approval and clarification answers resume an interrupted turn; they do not advance to the next scripted prompt.

Web server and routing: Uvicorn and FastAPI

Uvicorn is the web server. It listens for HTTP connections and runs the FastAPI application. The launcher calls uvicorn.run(app, host="127.0.0.1", port=port). Uvicorn and FastAPI communicate through ASGI, the asynchronous interface between a Python web server and its application.

FastAPI is the web application framework. It matches URLs and HTTP methods to handlers, such as GET /api/samples and POST /api/chat/{thread_id}. It also validates declared request models and supports responses, middleware, and application startup/shutdown. Our handlers manage sessions and pass chat requests to WebConversation; StreamingResponse sends the resulting AG-UI events back as Server-Sent Events (SSE).

Request path: Browser → Uvicorn → FastAPI route handler → WebConversation → LangGraphAgent → workflow. Calling FastAPI the router describes one of its responsibilities; Uvicorn owns the network listener.

Source: HTTP application and server startup.

Runtime boundaries

  • Persistence: Each conversation retains its own checkpointer. The harness attaches it to the graph; LangGraph handles checkpoint reads and writes. Direct callers supply their own checkpointer.
  • Tracing: Browser runs retain local TraceCapture recording when LangfuseCapture is enabled. The dotted connection marks the optional Langfuse callback.
  • MCP: The Wikipedia server exposes semantic_search_wikipedia over stdio. Direct and MCP retrieval use the same local search implementation.

All clients submit AG-UI run/resume requests and consume AG-UI events. Console and scripted clients call the Python driver in-process. Angular uses the JavaScript HttpAgent SDK and HTTP/SSE transport. AG-UI is the shared protocol, not an Angular-specific layer.

Supporting components compose with the driver. Client code submits requests and consumes events; only LangGraphAgent starts and resumes graph execution. Checkpoint inspection may read completed state for reports or tests, but must not execute the graph.

3. Interrupt and session lifecycle

Once a user submits a task, an agent normally continues its model-and-tool cycle until it can return an answer or the workflow reaches a stopping condition. It does not need another user message for every tool call. Some tasks, however, cannot continue without human input.

If information is missing or ambiguous, the agent can produce a clarification question. The custom workflow responds by calling LangGraph’s interrupt(), which pauses execution and returns control to the user through the client. The checkpointer retains the workflow state. When the user answers, the client submits a resume request on the same thread; LangGraph loads the checkpointed state and continues with that answer. This is a continuation of the task, rather than a new conversation.

In the quote sample, the agent supplies the question and its reason. The workflow retains the human’s answer alongside earlier questions and answers, then asks the agent to reassess the whole request. It may finish, ask another question, or follow the user’s cancellation choice.

3.1. Approval requests

An approval request lets a human authorize a critical action before it takes effect. The LLM chooses a tool and supplies its arguments; the sample’s approval middleware inspects that proposed call before the tool runs. When the call requires approval, the harness pauses execution and asks the client to present it to the human. The LLM does not decide whether its own action needs permission.

In the file-editing sample, critical actions are identified by tool name. The workflow declares RESTRICTED_TOOLS = frozenset({"write_file", "edit_file"}) and passes this set to RestrictedToolApproval when it builds the agent. The middleware’s after_model hook checks each proposed call against that set. This makes file writes subject to approval while reads of the configured documents need no approval. Adding another tool name to the set subjects that tool to the same policy; the classification is explicit code, not an instruction in the system prompt.

With the default always-ask mode, a restricted call triggers a LangGraph interrupt containing the tool name and exact arguments. The console or Angular client presents the proposal and collects an approval, rejection, or cancellation. Approval releases the call for execution, subject to the tool’s own validation. Rejection prevents that call and returns a rejection result to the agent, which can continue the conversation. Cancellation ends the workflow without undoing earlier completed actions. The explicitly selected autoapprove mode permits restricted calls without a human pause.

The clients and driver exchange official RunAgentInput objects, resume entries, and interrupt outcomes. The application’s shared payload contract describes the interaction itself—approval or question—without terminal text formatting, HTML, or callbacks. An interrupt payload uses kind: approval with tool arguments and cancellation choice, or kind: question with question text and a cancellation choice. The adapter preserves this payload in interrupt metadata. Clients answer with a resolved AG-UI resume entry whose payload is the workflow response, including explicit cancellation sentinels.

Resume semantics. A resume continues the pending interaction rather than creating a new user turn. Preserve thread and interrupt identity, give each run its own run ID, and do not append a duplicate request. LangGraph may replay the interrupted node from its start. Keep side effects outside replayed approval code and verify that completed model calls and writes are not repeated.

Cancellation and transport interruption. Workflow cancellation follows graph-defined semantics and does not undo earlier writes. Stop aborts a transport/run; an in-flight synchronous tool or provider request may still finish. It is not an approval response and does not guarantee rollback. Recovery after an aborted run must be explicit rather than silently replaying it.

4. AG-UI protocol

AG-UI (Agent–User Interaction) defines the structured requests and events exchanged between an agent application and its clients. A client submits a request to start or resume a run. The application returns a stream of events describing what happens during that run.

An event is a typed data object, not a line of display text. For example, a text-message event carries part of an assistant response; a tool-call event identifies a proposed call and its arguments; a run event identifies execution starting, finishing, or failing. The client interprets these objects to update its presentation.

ExchangeUse in these samples
Run requestSupplies the user message, thread identity, and a new run ID.
Message and tool-call eventsExpose assistant output and tool activity as execution proceeds.
Interrupted outcomeIdentifies a pending approval or clarification and carries the workflow’s interaction payload.
Resume requestSupplies the response and interrupt ID on the same thread, allowing the paused workflow to continue.
Completion or error eventAllows the client to distinguish a completed run from a failed run. An interrupted outcome is a normal pause.

LangGraphAgent provides the LangGraph integration: it starts or resumes the compiled graph and converts execution activity into AG-UI events. LangGraph executes the graph’s nodes and edges and maintains checkpoint state. The workflow decides when approval is required and which context to retain.

The protocol is shared across transports. Console and scripted clients exchange Python objects with the driver in process. Angular’s HttpAgent sends requests over HTTP and receives serialized events through Server-Sent Events (SSE). Both paths use the same run, interruption, and resume semantics.

5. Backends

A backend implements the storage or execution operations behind DeepAgents’ native tools. Workflows select a backend and pass it through a parameter dictionary; the agent forwards it to create_deep_agent(backend=...). For a LangChain agent, the workflow places the backend on the relevant DeepAgents middleware instead. The backend determines what a file path means and which operations it supports.

BackendOrigin and useAccess and limits
StateBackendStandard DeepAgents backend. Used by chat, reference-chat, investigation, delegating-parent, and Wikipedia MCP agents.Reads and writes virtual files in graph state. These tools do not access arbitrary host files. Checkpoints retain virtual file state according to the caller’s persistence configuration.
FileAccessBackendOur backend for the file editor.Maps /source.txt and /target.txt to two configured local paths. Both support reading; only the target supports writing and editing. It implements no shell execution. Approval comes from separate middleware.
ShellBackendOur backend for the shell agent.Uses standard FilesystemBackend for file tools and implements SandboxBackendProtocol for execute. Commands run locally as the current user with the inherited environment. A working directory is not an OS sandbox; shell commands can access locations outside it. This sample has no approval gate.

FileAccessBackend also delegates its allowed operations to the standard FilesystemBackend. Custom backends adapt native tools; they do not define additional model-facing tools.

6. Middleware

Middleware customizes execution around model calls and tool calls. It can supply tools, prepare model context, inspect model responses, or control whether a requested tool executes.

ConfigurationResponsibilityEffect in these samples
tools=[...]Register callable actions for the model to select.Provides application tools such as reference lookup. With create_deep_agent(), this list adds to built-in tools; an empty list does not remove built-ins.
middleware=[...]Configure behavior around agent execution, optionally supplying tools.Adds approval checks or delegation. create_deep_agent() also installs its default middleware.
backend=...Supply implementations for native storage and execution operations.Chooses virtual state files, the configured source and target, or local shell execution.

Standard middleware

  • Filesystem middleware: DeepAgents supplies native file tools and connects them to the selected backend. Default file tools can read and write virtual files with StateBackend; host access depends on the backend.
  • Subagent middleware: supplies the task tool and executes registered specialists. Our dispatcher installs SubAgentMiddleware directly on create_agent() to expose only its registered experts.
  • Context middleware: DeepAgents includes summarization and tool-call history repair. These support the agent loop without being application-defined tools.

Plain create_agent() does not automatically install the DeepAgents middleware stack. Each declarative specialist has its own tools, and DeepAgents adds standard child middleware when compiling it. An already compiled specialist retains its own graph configuration.

Our custom approval middleware

RestrictedToolApproval adds no tools. The file-approval workflow configures it with the mutation tool names, approval mode, and target path.

HookPurpose
before_modelCaptures an initial target snapshot if none exists in state.
after_modelInspects proposed mutations. In always-ask mode, interrupts for approve, reject, or cancel; autoapprove skips the human question. Cancellation ends the graph and resolves pending calls without executing them.
wrap_tool_call / awrap_tool_callReject unsupported tools, guard mutations against a changed target, and retain target observations from reads. Both execution paths apply the same policy.

The file-approval sequence diagram shows the model, approval, and native tool execution handoffs. The caller retains the checkpointer across interruptions and resumes. Snapshot comparison and writing are not atomic, and cancellation does not undo earlier writes.

LangChain provides standard HumanInTheLoopMiddleware, but this sample uses our custom middleware for its explicit cancellation and target-observation behavior. Prompt instructions guide the model; middleware and backend checks enforce this sample’s execution policy.

Source: RestrictedToolApproval · workflow configuration · standard delegation middleware. Checks: approval and resume tests · browser execution tests.

DeepAgents’ create_deep_agent builds an agent with standard middleware and tools.

from deepagents import create_deep_agent

agent = create_deep_agent(model=model)

This constructor includes DeepAgents' default middleware and tools, including filesystem and delegation. Their definitions contribute to model input even when no tool is called. Estimates should reflect that actual configuration.

Workflow configuration

The workflow selects dependencies and passes a plain dictionary to each agent:

parameters = {
    "model": model,
    "backend": backend,
    "middleware": [approval_middleware],
    "checkpointer": checkpointer,
}
agent = build_agent(parameters)

These variables are instances created or selected by the workflow. Include only settings needed by the receiving agent. Each independently constructed agent receives its own configuration from the workflow.

Defining tools

The agent constructor adds its instructions and domain tools:

from deepagents import create_deep_agent
from agent_runtime.tools.echo_tool import echo_tool


def build_agent(parameters: dict):
    return create_deep_agent(**parameters, tools=[echo_tool])

**parameters unpacks dictionary entries as keyword arguments: {"model": model, "backend": backend} becomes model=model, backend=backend. Middleware and checkpointers are passed the same way. Do not repeat a keyword already in the dictionary; Python rejects duplicate arguments.

Providing an agent-specific model

A workflow can normally use the same model throughout, passing it to each agent’s constructor through parameters["model"]. Some roles benefit from a different choice: a more capable model may improve quality for particularly complex work, while a lower-cost model may be sufficient for simple work. In that case, the agent constructor can provision the model for its own role.

This illustrative constructor uses SPECIALIST_MODEL to select the role’s OpenAI model. Set it to an available model suited to the role, and load it and OPENAI_API_KEY into the environment before constructing the agent:

import os

from deepagents import create_deep_agent
from langchain_openai import ChatOpenAI


def build_agent(parameters: dict):
    """Construct a specialist with a model selected for its own role."""
    # Provision this role's model once when building the agent, not on each turn.
    # The application loads SPECIALIST_MODEL and OPENAI_API_KEY beforehand.
    specialist_model = ChatOpenAI(
        model=os.environ["SPECIALIST_MODEL"],
        use_responses_api=True,
        max_tokens=2048,
        timeout=60,
        max_retries=0,
    )

    # Copy the workflow settings so other agents retain their shared model.
    # Replacing the dictionary entry also avoids a duplicate model keyword.
    agent_parameters = {**parameters, "model": specialist_model}
    return create_deep_agent(
        **agent_parameters,
        name="specialist_agent",
        system_prompt="Analyze the assigned problem and explain your conclusions.",
    )

The constructor replaces only the model in a copy of the workflow’s parameter dictionary; the supplied backend, middleware, and checkpointer still reach the agent. Other agents continue to use the workflow’s shared model. The same replacement pattern works with create_agent() when the dictionary contains only arguments that constructor accepts. Creating the model adapter configures the client; generation happens when the agent runs.

Minimal agents

Use LangChain’s create_agent() to build an agent with only the tools and middleware you provide. This example creates an agent with no tools or middleware:

from langchain.agents import create_agent

agent = create_agent(model=model)

LangChain has no backend keyword. The workflow supplies a backend through the DeepAgents middleware that uses it:

from deepagents.middleware.filesystem import FilesystemMiddleware

parameters = {
    "model": model,
    "middleware": [
        FilesystemMiddleware(backend=backend, tools=["read_file"]),
    ],
}
agent = create_agent(**parameters)

The file-approval workflow uses this pattern with read, write, and edit tools, its approval middleware, and a checkpointer. This also keeps delegation out of that editor, where a child must not bypass approval. The author, judge, and quote roles use LangChain agent loops with workflow-supplied middleware. Their adapters translate domain inputs and outputs. The outer LangGraph workflows own routing, retained context, and human interaction.

Tool definitions cost input tokens even when unused. Select a native constructor and middleware appropriate to the lesson, and account for what they actually send. Live reports retain provider usage when available; missing usage and prices remain explicit.

Agent construction and delegation

SubAgent and CompiledSubAgent are typed configuration dictionaries. The former supplies a specialist specification to compile; the latter references an existing runnable graph. During execution, the parent model selects a specialist through task, and the middleware runs it and returns its answer to the parent.

The dispatcher uses SubAgentMiddleware directly to expose only its registered experts. The file editor uses LangChain’s create_agent() with DeepAgents filesystem middleware and a bounded backend. The claims agent and direct Wikipedia RAG agent use LangChain’s create_agent().

Execution and persistence

LangGraphAgent belongs to the AG-UI integration. It starts or resumes the compiled graph and translates execution into client events. DeepAgents constructs agents and supplies delegation behavior inside that graph.

StateBackend provides the virtual filesystem used by DeepAgents tools. The conversation-owned InMemorySaver retains graph checkpoints across turns and pauses, including any virtual file state. The file editor uses native file tools with FileAccessBackend and RestrictedToolApproval to access configured local documents under workflow approval policy.

Scripted execution

Scripted execution replaces live model responses with predefined answers and tool calls. It makes demonstrations repeatable and lets tests exercise specific workflow paths, such as tool use, approval, and error handling, without waiting for a provider or paying for model calls. This helps isolate application behavior from variation in model responses.

The workflow still runs its real tools and policies; the scripted model controls which actions it requests. These runs demonstrate that the application handles the prepared scenario. They do not establish how well a live model reasons, chooses tools, or answers unfamiliar questions.

For scripted execution, keep a way to inject the scripted model instead. When combining models in one workflow, reporting must use each call’s actual model identity and usage so that costs are attributed to the correct model.

Scripted user inputs are a separate choice: a prepared conversation can also run against a live model. In the sample runner, --simulated explicitly selects scripted models; the default uses real provider models. Keep simulated results clearly identified so they are not mistaken for live quality or cost evidence.

Give an agent that provisions its own model an explicit override parameter. In this example, the constructor checks that override before creating the live model. The scripted path therefore needs neither provider credentials nor a provider request:

import os

from langchain.agents import create_agent
from langchain_core.messages import AIMessage, HumanMessage
from langchain_openai import ChatOpenAI

from agent_runtime.harness.simulated_model import ScriptedChatModel


# Agent constructor code: defines how the agent is built.
def build_agent(parameters: dict, *, model_override=None):
    """Use this role's live model unless the caller injects a replacement."""
    # Check the override first so offline runs need no provider credentials.
    model = model_override
    if model is None:
        model = ChatOpenAI(
            model=os.environ["SPECIALIST_MODEL"],
            use_responses_api=True,
            max_tokens=2048,
            timeout=60,
            max_retries=0,
        )

    # Keep workflow settings intact and pass the selected model exactly once.
    agent_parameters = {**parameters, "model": model}
    return create_agent(
        **agent_parameters,
        system_prompt="Answer the user's question concisely.",
    )


# Test code: supplies a scripted model, runs the agent, and checks its answer.
# This belongs in the test, separate from the agent constructor.
scripted_model = ScriptedChatModel(
    responses=[AIMessage(content="Paris is the capital of France.")],
)
agent = build_agent({}, model_override=scripted_model)
result = agent.invoke({
    "messages": [HumanMessage(content="What is the capital of France?")],
})
assert result["messages"][-1].content == "Paris is the capital of France."

For live execution, call build_agent(parameters) after configuring SPECIALIST_MODEL and provider credentials. For scripted execution, pass a fresh ScriptedChatModel through model_override. The workflow parameter dictionary must contain only settings accepted by create_agent(). An agent that already uses the workflow-supplied model can simply receive the scripted model in parameters["model"].

This short script supplies one final answer. To exercise tools, provide an AIMessage with tool calls followed by the next scripted response; the graph executes the real tools between those responses. Give each independently constructed agent its own response sequence. The fixed answer here checks execution wiring, not whether a model can answer the question.

8.11. Claims context strategies

One agent with two workflow context strategies

Reports: Naive: HTML report · Excel report · Managed: HTML report · Excel report

A fictional claim store is authoritative. Managed mode detects a successful edit and uses the agent’s context-dependency knowledge to remove stale claim content and related prose. Unaffected policy evidence can remain. The agent chooses whether to reread the claim on a follow-up; the application must not preload it.

Execution requirements. The context strategy executes in a graph node. Keep the context audit separate from working memory. Offline fixtures prove mechanics, not that naive mode must answer incorrectly.

How working context changes after an edit

The sample keeps three distinct forms of information. ClaimStore holds the current claim and policy records. ClaimsState.working holds the messages supplied to the next agent invocation. The display transcript and ContextAudit retain historical evidence separately, subject to content-capture settings. Clearing working context does not delete the current claim or rewind its edits.

In managed mode, the workflow checks for a successful edit when the agent turn completes. It then discards claim-dependent messages and retains valid policy tool exchanges plus an invalidation notice. It does not clear context between individual tool calls within that turn. A later agent-selected read_claim() returns the complete current record, adding fresh evidence to working context.

A second edit after that purge needs a fresh read because edit_claim() requires a previously read revision. Thus the safe sequence across turns is read → edit and discard → read current revision → edit and discard → read current claim. Multiple edits within one turn may use the revision returned by the preceding successful edit; their context is purged when that turn ends.

The audit is not a raw-message collection for automatically rebuilding model context: doing that would reintroduce stale snapshots. A richer context strategy could retain selected user preferences or structured facts with explicit validity rules, but this sample uses the current store record and genuine tool reads. Its coarse purge also removes earlier conversational preferences.

8.12. Simple chat with Langfuse

Langfuse provides tools for exploring how an LLM application behaved during a run. This sample reuses the simple-chat agent and workflow. The application attaches a Langfuse callback handler and configures where execution traces are recorded.

A trace records the activities that make up a run, including model calls, their timing, and the inputs, outputs, token usage, and costs available under the recording configuration. Engineers can inspect these details to investigate an unexpected answer, a slow operation, or an expensive conversation. Langfuse’s session view groups related traces and provides a replay of the recorded interaction. A captured model call can also be opened in the Playground to rerun it or compare changes to its prompt and model settings. This supports debugging individual calls; it does not automatically replay the entire workflow and its external side effects.

Langfuse data can also become the input to an HTML report. Its Observations API exposes recorded spans and model calls that an importer could translate into this project’s report data format. That would let us generate a shareable report from a selected production run after it has completed, without rerunning the application. The importer is not implemented in this sample; the sample demonstrates sending traces to Langfuse. A generated report would contain only the evidence actually captured, preserving missing usage or pricing as unknown.

The application configures Langfuse credentials and content capture, attaches the callback handler, and associates observations with their conversation and turn. It also flushes pending observations and closes the tracing client when recording ends. These responsibilities stay outside the agent’s prompts and business logic.
